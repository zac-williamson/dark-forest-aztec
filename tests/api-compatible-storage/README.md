# Original storage API regression tests

`run.mjs` deploys fresh original stores and fresh facade namespaces on the existing candidate backend. It does not modify the shared action-fee fixtures, Config, or World namespace. It compares actual original and candidate setter/constructor/batch event fields and ordering, full-state hashes, zero/presence semantics, arrival records and allocation, independent namespace updates, authorization-list mutation, admin transfer, spoofed callback rejection, and one-time binding.

All six suites use separate fresh PXEs with `proverEnabled: false`. Both native worker limits stay at two threads. Transaction proving, native/browser profiling, and prove-and-mine remain disabled. Reports have distinct `-candidate-v5.json` names. Choose a fresh explicit third-argument output path for every rerun, preserving prior evidence. Setup transactions affect isolated namespaces and System clones; read-only and trust suites send no transactions. Each tested live class must match its exact native artifact.

V5 `run.mjs` independently checks physical storage as well as getters/events. Before creating a wallet, it validates each compiled contract's own storage declaration: all nine facades own `local_roots` at slot 3, and Backend admins/grants/Arrival payload/counter remain at slots 2/3/7/8. It calls `observeLocalRoot` after every typed-state verification, constructor, overwrite, and independent namespace mutation. The expected value is the full Poseidon hash of the exact serialized fixture state, including original fields and inactive padding; it is never copied from a getter.

Seven permission checkpoints call `observeNamespacePermission` after binding, grant additions/removals, and admin transfers, including the zero address. They compare the raw grant word to exactly 0 or 1 and the raw admin Field to the explicit transfer target, as well as effective authorization. This detects a stale admin masked by an existing grant. All previously seeded roots must remain unchanged through these operations. Every observation records its block, namespace, raw values, and independently derived expectation. V4 replay skips these V5 physical reads. Five offline integration tests, including actual frozen V4 layouts, pass; see [physical-storage-readiness-v5.json](../../docs/api-compatibility/physical-storage-readiness-v5.json).

V5 trust coverage validates seven direct settlement routes and two unified plan routes against the compiled artifact, including direct Reveal/Give paths and removal of obsolete delegated/batch endpoints. Raw facade callbacks must retain the additional full Field root immediately after the ID. Injected contract-sender guard probes are explicitly labeled node-only simulations, not valid account transactions. Ordinary hostile calls and complete private-entry fee transactions supply separate evidence.

`batch-caller.mjs` adds essential custom-verifier coverage beyond the previous suites. It checks original zero-count Arrival, Artifact, and Location calls for Core Refresh, Vault Give, and Move, including false-return propagation and the exact original System caller. Mixed source-zero/target-one and source-one/target-zero Move fixtures distinguish call order. Nonzero batches with all-zero artifact IDs are also covered. The fixture checks every ID/hash word, including all 40 inactive words at count zero. It is genuinely native-processed with zero private functions, and selector `0x47c7b238` matches all three original stores. All 238 checks passed. The completed report retains 76 successful controls/Core checks from a preserved earlier run; resume revalidated all 61 setup receipts and 17 isolated classes before the remaining 162 checks. Two harness errors (assertion ABI decoding and Vault parameter-name mapping) were corrected and archived separately; neither was a contract behavior mismatch. See [caller-batch/README.md](caller-batch/README.md) and [batch-caller-readiness-v5.json](../../docs/api-compatibility/batch-caller-readiness-v5.json).

These suites establish compatibility, not successful gameplay fees or proof latency. The separate 45-pair fee runner measures complete mined transactions. All six final V5 runtime reports show actual successful checks; these results do not transfer automatically to another artifact version.

## V4: frozen evidence and historical commands

The frozen V4 run passed 620 checks: reader 162, storage 306, caller-sensitive Config 34, inactive Location 20, and trust 98. Exact prior runner sources, logs, fixture artifacts, and reports are preserved under `/tmp/df-api-compatible-v4/runtime`, with `runtime-manifest.json` in its parent directory. [runtime-readiness-v4.json](../../docs/api-compatibility/runtime-readiness-v4.json) describes that completed run. It does not cover the newly discovered empty-batch verifier behavior or validate V5. The following are historical V4 invocations; choose a new report path before replaying them.

```sh
NODE_BACKEND=js LOG_LEVEL=error node --import ./node_modules/tsx/dist/loader.mjs tests/api-compatible-storage/read-only.mjs candidate-v4 /tmp/df-api-compatible-v4-native
NODE_BACKEND=js LOG_LEVEL=error node --import ./node_modules/tsx/dist/loader.mjs tests/api-compatible-storage/trust.mjs candidate-v4 /tmp/df-api-compatible-v4-native
NODE_BACKEND=js LOG_LEVEL=error node --import ./node_modules/tsx/dist/loader.mjs tests/api-compatible-storage/run.mjs candidate-v4 /tmp/df-api-compatible-v4-native
```

Run these serially only after the final candidate deployment is ready and the fee owner explicitly releases the validation interval. The new paired Find case uses its own `v4` historical anchor; do not advance the chain with isolated setup transactions before that case finishes. The original ephemeral chain was restarted after v1 evidence was archived; its old addresses are no longer usable. The variant resolves to `experiments/api-compatible-benchmark/.state/candidate-v4-deployments.json`. Each report has a separate `-candidate-v4.json` suffix, preserving earlier results. The defaults also select `candidate-v4` and `/tmp/df-api-compatible-v4-native`. An explicit deployment JSON path remains accepted as the first argument, with an optional output path as the third. Environment equivalents are `STORAGE_VARIANT`, `STORAGE_DEPLOYMENTS`, `STORAGE_ARTIFACTS` and `STORAGE_OUTPUT`.

All suites use `proverEnabled: false`; no transaction proofs, profiling, or proof-and-mine workflow is invoked. Each tested facade/System/backend artifact is compared with the actual deployed class ID before use; newly deployed isolated test contracts are checked too. Read-only checks register only the nine facades and require their backend address to match the selected deployment.

The first command creates a fresh PXE and registers only the nine facade artifacts. It checks the original public/utility reader APIs while verifying that the backend artifact remains unregistered. No nested utility authorization hook is configured. Utilities read their anchor block; public readers use constrained VM SLOADs and must observe preceding writes in the same transaction. The storage suite tests that distinction for all nine original store APIs. Verify the shared layout constants separately:

```sh
python3 tests/api-compatibility/verify_backend_layout.py
```

For V4, `trust.mjs` validates all eight compiled backend settlement boundaries and the Core compact widths 56/144 and Move widths 539/337 before simulating rejection cases. Obsolete compact widths 84/217 fail this check. It only simulates rejection cases and can run without changing the fee fixtures. It requires the complete candidate deployment, including both settlement workers. It checks forged prepared calls, accounts claiming actual System addresses in delegated commits, worker caller impersonation, the original and added `only_self` continuations, both typed and raw event callbacks, unauthorized wiring changes, and attempts to bind or write a canonical namespace without an authenticated facade. Callback arguments are constructed from the final ABI, including individually declared raw fields. `run.mjs` additionally verifies pending facade deployments cannot write before binding or bind a zero backend.

Dependencies are pinned to SDK 5.2.0. `node_modules` is ignored, including local runtime symlinks. `AZTEC_NODE_URL` defaults to the isolated local node on port 8097. Every suite creates its own isolated PXE directory; it never opens the fee runner's `/tmp/df-api-compatible-wallet52-v2` wallet. These are local test deployments and simulated rejection checks; the storage suite does not claim real private gameplay proof coverage.

The repository's `tsx` loader supplies the JSON-module compatibility required by the pinned account artifacts on current Node versions. The World default witness follows the original `World::zero()` definition, including its radius of 53,000; an all-numeric-zero World is a distinct valid state.

The arrival overwrite regression preserves full Field identity values while switching all numeric values through maximum → ordinary compact → maximum → explicit zero at a nonzero ID. Every step checks both original public and utility getters against the full eleven-field expected record, its original full-record root, and the exact original event. A same-transaction full-to-compact overwrite also checks the public getter and pending zero-word clearing. These Arrival checks passed against both frozen V4 and V5, with V5 additionally checking the independent physical facade roots.

The compiled Move transport checker is in this directory (not `tests/api-compatibility`). It validates the actual compiled backend selector, FieldBuffer widths, and the original System continuation's `only_self` protection against the generated transport manifest. It opens no wallet or node and does not generate a proof:

```sh
NODE_BACKEND=js LOG_LEVEL=error node --import ./node_modules/tsx/dist/loader.mjs tests/api-compatible-storage/verify-move-transport.mjs /tmp/df-api-compatible-v4-native/game_state_backend-GameStateBackend.json /tmp/df-api-compatible-v4-native/move-Move.json
```

Pass the full native, postprocessed artifacts from the same completed build. The `PUBLIC-ONLY` size-probe artifacts are nondeployable and must never be used for these runtime checks. The same command accepts another explicit backend/Move artifact pair during a build; the raw pre-transpilation compiler output is not a replacement for the native artifacts.

`config-caller.mjs` checks caller-sensitive Config implementations through the original private Core and Move APIs. It deploys isolated original/candidate System clones and the public-only `CallerSensitiveConfig`. The 34 expected runtime checks cover Move empty/full paths at both Config selectors, fresh/general/padded initialization, Reveal, Withdraw, and Upgrade at both upgrade selectors, plus direct-account caller rejection. Upgrade uses isolated canonically bound Planet, PlanetArtifacts, PlanetEvents, and World namespaces seeded from the original fixture, preserving the state checks that precede Config. Every sentinel occurs before game-state writes. No shared Config, World, or writer permissions are changed.

```sh
NODE_BACKEND=js LOG_LEVEL=error node --import ./node_modules/tsx/dist/loader.mjs tests/api-compatible-storage/config-caller.mjs candidate-v4 /tmp/df-api-compatible-v4-native
```

Run only after final deployment, rebuilding the expanded public-only Config fixture, and the coordinator's local mutation-window release. The original Init/Move ordinary fixtures default to `baseline-v2`; full Move uses the archived `baseline-move-20.json`, and Upgrade/Withdraw/Reveal use `baseline-<method>-ordinary.json`. `CALLER_INITIALIZE_FIXTURE`, `CALLER_MOVE_EMPTY_FIXTURE`, `CALLER_MOVE_FULL_FIXTURE`, `CALLER_UPGRADE_FIXTURE`, `CALLER_WITHDRAW_FIXTURE`, and `CALLER_REVEAL_FIXTURE` select explicit inputs. Only original private witnesses are reused, never their old-chain addresses. General and padded initialization use the benchmark's `buildCoreCase` generator. Artifact, original input, and derived input hashes are recorded.

`location-caller.mjs` adds 20 expected runtime checks for original/final Refresh and Move. Its custom storage contract checks the actual caller, every inactive location field, and Move source/target batch order before a final sentinel. A changed inactive value must trigger a different rejection. It uses isolated canonical namespaces and the original private APIs, then checks that roots, arrival counter, and custom call counter remain unchanged after each simulation. See [caller-location/README.md](caller-location/README.md) for fixture details and invocation.

Both suites use `proverEnabled: false`, generate no transaction proofs, and send no gameplay transactions. Setup deployments, namespace binding, seeding, and wiring are real isolated local transactions. Their runtime results are compatibility evidence, not successful settlement fees or proof latency. `CALLER_CONFIG_ARTIFACT` and `CALLER_LOCATION_ARTIFACT` select the respective full native public-only test fixture artifacts. Prior live evidence does not validate the final candidate revision.
